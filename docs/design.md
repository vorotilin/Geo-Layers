# Design doc — apc-layers

Этап M0. Согласуется с заказчиком до начала кода.
Объём: 2–4 страницы.

## 1. Границы сервиса

### Что сервис делает

- Принимает файлы сеток данных поставщиков (GeoJSON, NDJSON, CSV, XLSX, GeoPackage)
  через загрузку, ссылку или объект в S3. Описание слоя: название, единица измерения,
  период, поставщик, правило агрегации. Несколько числовых колонок = несколько слоёв.
- Принимает наборы точек (CSV, XLSX, GeoJSON, NDJSON): координаты обязательны,
  вес и категория — по желанию. Хранит с версиями и пополнением.
- Строит из точек слои тремя способами: тепловая карта (KDE с полосой в метрах
  и режимом радиуса в пикселях), биннинг в сетку/H3, картограмма по полигонам.
  Нормировки: как есть, на км², доля от общего, на значение другого слоя.
- Хранит данные в своей модели: набор → слой → версия (период) → значения по ячейкам.
  Геометрия ячеек хранится один раз.
- Считает статистику версии (min/max, квантили, гистограмма) и разбивает на классы:
  равные интервалы, квантили, логарифм, ручные границы. Желательно — Jenks.
- Настраивает стиль без перезагрузки данных: палитра, число классов, непрозрачность,
  цвет «нет данных», правила для мелких масштабов. Легенда строится из того же стиля,
  что и картинки.
- Отдаёт растровые тайлы PNG с прозрачностью в схеме XYZ, 256 px и @2x,
  в двух сетках: EPSG:3857 (Web Mercator) и EPSG:3395 (эллиптический Меркатор,
  как в Яндекс.Картах v3). На мелких масштабах рисует агрегат. Правильные заголовки
  кэширования: Cache-Control, ETag, 304.
- Отдаёт API данных: каталог слоёв и версий с легендой; значение в точке по всем слоям;
  пакет точек (тысячи координат → значения); агрегат по полигону или bbox
  (среднее, сумма, min/max, число ячеек, доля покрытия); рейтинг ячеек или полигонов.
- Версионирует: загрузка создаёт черновик, публикация делает его актуальным, старые
  версии доступны явно, повторная загрузка того же файла не создаёт дубликат;
  пополнение набора точек даёт новую версию слоя.
- Доступ: управляющие вызовы по токену; тайлы и значения по подписанным ссылкам
  со сроком действия (HMAC от пути и срока); CORS; лимиты частоты; наборы точек
  и их слои приватны в рамках namespace.
- Веб-интерфейс: импорт сетки и точек, построение слоя из точек, загрузка полигонов,
  каталог слоёв и версий с публикацией, форма стиля с предпросмотром, карта на MapLibre,
  список заданий с повтором.
- Служебное: прогрев кэша тайлов по области и зумам, сброс кэша, повтор задания,
  метрики, логи, /health, /ready.

### Что сервис НЕ делает

- Не ходит в базу платформы.
- Не знает сущностей платформы (рекламные конструкции, заказы, календарь занятости).
- Не принимает бизнес-решений — только считает, проверяет, преобразует и честно
  отвечает, что получилось.
- Не раздаёт лицензионные данные поставщика без подписи.

### Ограничения

- Стек свободный, защищается в design doc; заказчик вправе отклонить выбор, если он
  мешает эксплуатации (экзотика без пакетов, нет Docker-образов, лицензии).
- Работает в Docker на Linux x86_64, профиль «2 vCPU / 4 ГБ / без GPU» обязателен.
  GPU, если используется, — ускорение, а не требование.
- Никаких платных внешних сервисов: всё считается локально.
- Данные поставщика лицензионные.

## 2. Черновик API

Все маршруты под `/v1/`. JSON, UTF-8, `Content-Type: application/json`.
Файлы — `multipart/form-data` или по ссылке. Неизвестные поля игнорируются,
перечисления открытые. Время — ISO 8601 с таймзоной, идентификаторы — непрозрачные
строки, денег в API нет. Заголовок `X-Request-Id` принимаем или генерируем,
возвращаем, пишем в лог.

Ошибки — единая форма:
`{ "error": "machine_slug", "message": "текст для человека", "details": { ... } }`.
Коды: 400 кривой запрос, 401 нет/плохой токен, 403 токену нельзя, 404 нет объекта,
409 конфликт состояния, 413 слишком большой файл, 422 тело валидно синтаксически,
но не по смыслу, 429 лимит (с Retry-After), 5xx сбой сервиса.

Долгие операции — задания (jobs): `202 Accepted` с `{ "job_id": "...", "status_url": "..." }`,
затем `GET /v1/jobs/{id}` со статусом `queued | running | succeeded | failed`,
прогрессом (0-100 или шаги) и результатом или ошибкой. По желанию клиента — callback
(`callback_url` в запросе): `POST` с результатом, подписанный, с повторами при ошибке
(не меньше 5 попыток с нарастающей задержкой). Опрос статуса и callback могут идти
одновременно — результат идемпотентен.

Идемпотентность: заголовок `Idempotency-Key` или дедупликация по содержимому
(хэш файла + параметры). Механизм выбираем и описываем в API.

### Управление и загрузка

- `POST /v1/datasets` — загрузка сетки (файл, ссылка или объект в S3) с описанием
  слоя: название, единица измерения, период, поставщик, правило агрегации, маппинг колонок.
  Ответ: `202` с заданием.
- `POST /v1/datasets/{id}/versions` — новая версия (период) набора.
- `POST /v1/datasets/{id}/versions/{v}/publish` — публикация черновика.
- `POST /v1/points` — загрузка набора точек (CSV, XLSX, GeoJSON, NDJSON), маппинг полей.
- `POST /v1/points/{id}/append` — пополнение набора точек (новая версия).
- `POST /v1/layers` — построение слоя из точек: метод (KDE / биннинг / картограмма),
  параметры (полоса в метрах или радиус в пикселях, шаг сетки или уровень H3, полигоны,
  нормировка), категории, фильтры. Ответ: `202` с заданием.
- `POST /v1/polygons` — загрузка полигонов (районы, свои области).
- `POST /v1/styles` — создание/обновление стиля слоя (палитра, классы, непрозрачность,
  цвет «нет данных», правила для мелких масштабов).
- `POST /v1/statistics` — расчёт статистики версии (min/max, квантили, гистограмма)
  и разбиение на классы (равные интервалы, квантили, логарифм, ручные границы, Jenks).

### Каталог и чтение данных

- `GET /v1/datasets` — каталог наборов (курсорная пагинация).
- `GET /v1/datasets/{id}/versions` — версии набора.
- `GET /v1/layers` — каталог слоёв с легендой (курсорная пагинация).
- `GET /v1/layers/{id}` — метаданные слоя: тип, версии, стиль, статистика.
- `GET /v1/layers/{id}/legend` — легенда, построенная из стиля.
- `GET /v1/values` — значение в точке по всем слоям. Тело: координата или список
  координат с id (пакет точек — тысячи за раз).
- `GET /v1/aggregate` — агрегат по полигону или bbox: среднее, сумма, min/max,
  число ячеек, доля покрытия.
- `GET /v1/rating` — рейтинг ячеек или полигонов по значению.

### Тайлы

- `GET /v1/layers/{id}/tiles/{z}/{x}/{y}.png` — растровый тайл PNG с прозрачностью,
  XYZ, 256 px и `@2x`. Параметр `crs=3857|3395` — сетка (по умолчанию 3857).
  На мелких масштабах — агрегат. Заголовки: `Cache-Control`, `ETag`, `304`.
  Публичные ссылки — подписанные (HMAC от пути и `exp`).
- `GET /v1/layers/{id}/tiles/{z}/{x}/{y}.mvt` — (желательно) векторный тайл
  с атрибутом значения для MapLibre.

### Задания и служебное

- `GET /v1/jobs/{id}` — статус задания: `queued | running | succeeded | failed`,
  прогресс, результат или ошибка.
- `POST /v1/jobs/{id}/retry` — повтор задания.
- `POST /v1/cache/warm` — прогрев кэша тайлов по области и зумам.
- `POST /v1/cache/reset` — сброс кэша.
- `GET /health` — жив, версия сборки.
- `GET /ready` — готов: зависимости доступны.
- `GET /metrics` — Prometheus: счётчики запросов, длительности, очередь, кэш.
- `GET /docs` — Swagger UI (dev-режим).

### Аутентификация и доступ

- Вызовы в сервис — `Authorization: Bearer <token>`. Токенов несколько, у каждого
  область (`admin`, `write`, `read`), отзыв без перезапуска, хранение хэшем.
- Callback'и из сервиса в платформу подписываются: `X-Apc-Timestamp` (unix-секунды)
  и `X-Apc-Signature: sha256=HMAC_SHA256("{timestamp}.{raw_body}", secret)`,
  подпись от сырого тела. Платформа отвергает подпись старше 5 минут.
- Публичные ссылки (тайлы, превью) — подписанные URL со сроком действия
  (HMAC от пути и `exp`).
- CORS, rate limit на публичных и дорогих ручках, capы одновременных заданий на токен.
- Наборы точек и их слои приватны в рамках `namespace`.

### Веб-интерфейс

- Вход по токену или basic auth.
- Импорт сетки (файл или ссылка, форма манифеста, маппинг колонок, прогресс, отчёт об ошибках).
- Импорт точек (маппинг полей, предпросмотр).
- Построение слоя из точек (метод и параметры).
- Загрузка полигонов.
- Каталог слоёв и версий с публикацией и кнопкой «скопировать шаблон URL тайлов».
- Форма стиля с предпросмотром.
- Карта на MapLibre: слои, непрозрачность, легенда, значение под курсором, рейтинг,
  переключение версии, стиля и сетки.
- Список заданий с повтором.

Полный контракт — `openapi.yaml` (появится на M1), проверяется контрактными тестами
или генерацией из кода.

## 3. Схема данных

Данные хранятся в модели «набор → слой → версия (период) → значения по ячейкам».
Геометрия ячеек хранится один раз и переиспользуется между версиями и слоями.

### Сущности

- `dataset` — набор данных поставщика: идентификатор, название, поставщик,
  единица измерения, правило агрегации (`avg | sum | max | min`), namespace,
  дата создания.
- `layer` — слой: ссылка на dataset или на набор точек, тип
  (`grid | points | polygon | heatmap | binning | cartogram`), стиль по умолчанию,
  статус.
- `version` — версия слоя (период): ссылка на layer, период (`2023Q1`),
  статус (`draft | published | archived`), статистика (min/max, квантили, гистограмма),
  дата загрузки, хэш исходного файла (для дедупликации).
- `cell` — ячейка геометрии: `zone_id` (из поставщика) или собственный id,
  геометрия (полигон, квадрат, шестиугольник, H3-индекс, quadkey), CRS.
  Хранится один раз, привязывается к версиям через `value`.
- `value` — значение: ссылка на `cell`, ссылка на `version`, число `val`.
  Индекс по `(version_id, cell_id)`.
- `point_set` — набор точек: идентификатор, namespace, поля (id, name, category,
  lat, lng, weight, seats, дата — произвольные), версия, дата.
- `point` — точка: ссылка на `point_set`, координаты (lat/lng), вес, категория,
  произвольные поля.
- `polygon` — полигон (район, своя область): идентификатор, геометрия, название,
  ссылка на namespace.
- `style` — стиль слоя: палитра, число классов, метод разбиения
  (`equal | quantile | log | manual | jenks`), непрозрачность, цвет «нет данных»,
  правила для мелких масштабов.
- `job` — задание: тип, статус (`queued | running | succeeded | failed`),
  прогресс, входные параметры, результат или ошибка, `Idempotency-Key`.
- `token` — токен доступа: хэш, область (`admin | write | read`), namespace,
  статус (активен / отозван).

### Связи

- `dataset 1—N layer`
- `layer 1—N version`
- `version 1—N value`
- `cell 1—N value` (геометрия ячейки переиспользуется между версиями)
- `point_set 1—N point`
- `layer 1—1 style` (или несколько стилей на слой)
- `namespace 1—N dataset / point_set / polygon`

### Особенности

- Отсутствие ячейки — «неизвестно», не ноль. При агрегации это учитывается отдельно
  от значения 0.
- Повторная загрузка того же файла (совпадает хэш + параметры) не создаёт новую
  версию — возвращает существующую.
- Старые версии не удаляются, доступны явно по `version_id`.
- Для больших файлов (до 3 ГБ, миллионы ячеек) загрузка идёт потоково, без чтения
  целиком в память; ячейки пишутся батчами.
- CRS ячеек: хранение в исходной CRS поставщика, пересчёт в EPSG:3857 / EPSG:3395
  при рендере тайлов.

## 4. Стек с обоснованием

Стек выбирает команда и защищает здесь; заказчик вправе отклонить выбор, если он
мешает эксплуатации (экзотика без пакетов, нет Docker-образов, лицензии).

### Язык и фреймворк

- **Вариант A: Python + FastAPI.**
  Плюсы: быстрый старт, богатая экосистема для гео (GDAL, shapely, rasterio, numpy),
  Pillow для PNG, async из коробки, генерация OpenAPI, легко поднять веб-интерфейс
  (Jinja2 + HTMX). Минусы: медленнее на CPU-тяжёлых задачах, GIL — для тяжёлых
  вычислений нужны процессы/нативные расширения.
- **Вариант B: Go.**
  Плюсы: быстрый, один бинарник, хорошо для конкурентных тайлов, простой Docker.
  Минусы: беднее гео-экосистема, больше кода для простых вещей, дольше старт.
- **Вариант C: Node.js (NestJS).**
  Плюсы: быстро для I/O, единый язык с веб-интерфейсом. Минусы: гео-библиотеки
  слабее, тяжёлые вычисления в отдельных воркерах.

**Выбор:** Python + FastAPI. Обоснование: гео-задачи (парсинг GeoJSON, GDAL, H3,
растеризация) — сильная сторона Python; быстрый старт под срок; FastAPI даёт
OpenAPI и async. Тяжёлые задачи (растеризация тайлов, KDE) выносим в отдельные
процессы (Celery/ARQ + Redis), чтобы не блокировать API. См. `docs/decisions.md`.

### База данных

- **PostgreSQL + PostGIS.** Геометрии, пространственные индексы (GiST),
  агрегаты по bbox и полигонам, хранение миллионов ячеек. PostGIS — стандарт
  для гео, поддержка всех нужных CRS, `ST_Intersects`, `ST_AsMVT` для векторных тайлов.
- Альтернатива: SQLite + SpatiaLite — проще, но хуже для конкурентной записи
  и миллионов строк на профиле «2 vCPU / 4 ГБ».

**Выбор:** PostgreSQL + PostGIS.

### Очередь заданий

- **Redis + Celery (или ARQ).** Задания загрузки, растеризации, построения слоёв
  из точек, прогрева кэша. Прогресс задания пишется в БД, воркеры — тот же образ
  с другой командой (требование `common-requirements.md`).

### Кэш тайлов

- **Redis** для горячего кэша тайлов + **файловый кэш или MinIO** для持久ного.
  Заголовки `Cache-Control`, `ETag`, `304` на уровне API.

### Хранилище файлов

- **S3-совместимое (MinIO локально).** Входные файлы, превью, экспорты.
  В проде — любой S3.

### Веб-интерфейс

- **Jinja2 + HTMX** (без тяжёлого SPA) или **React** — на усмотрение команды.
  Карта — **MapLibre GL JS**.

### Контейнеризация

- Docker multi-stage, запуск не от root, `HEALTHCHECK`, зафиксированные версии
  зависимостей, lock-файл.
- `docker compose up` поднимает сервис, воркеры, PostgreSQL+PostGIS, Redis, MinIO.

### Ограничение профиля

- Профиль «2 vCPU / 4 ГБ / без GPU / Linux x86_64» обязателен. GPU — только
  ускорение, не требование. Тяжёлые задачи ограничиваем по CPU и памяти на процесс.

## 5. Риски

- **Большие файлы (до 3 ГБ, миллионы ячеек).** Риск: OOM, долгая загрузка.
  Митигация: потоковый парсинг (NDJSON, CSV построчно), батчевая запись,
  лимиты размера и времени, отдельный процесс с ограничением памяти.
- **Враждебные входные файлы.** Риск: декомпрессионные бомбы (zip, изображения),
  полиглоты, кривые заголовки. Митигация: лимиты размера и времени разбора,
  разбор в отдельном процессе без сети, вызов внешних утилит массивом аргументов,
  без сборки командной строки.
- **Разнообразие форматов поставщиков.** Риск: образец — только один поставщик,
  на приёмке будут «другие» данные (шаг 100 м–5 км, шестиугольники, произвольные
  полигоны, H3, quadkey, проекционные CRS). Митигация: абстракция «источник → ячейки»
  с адаптерами, тесты на синтетических данных разных типов, не проектировать под образец.
- **Производительность тайлов.** Риск: холодный тайл дольше 300 мс, не держим
  200 rps на 2 ядрах. Митигация: кэш тайлов, предварительная растеризация,
  агрегаты на мелких масштабах, бенчмарки скриптом из репозитория.
- **Две сетки (EPSG:3857 и EPSG:3395).** Риск: ошибки в пересчёте, несовпадение
  с Яндекс.Картами v3. Митигация: явные тесты на известных тайлах, сверка
  с эталонными картами.
- **Безопасность и лицензии.** Риск: утечка данных поставщика, несовместимые
  лицензии зависимостей. Митигация: подписанные URL, токены с областями,
  проверка лицензий в CI (gitleaks + лицензионный сканер), запрет библиотек
  с требованием раскрытия кода.
- **Сроки.** Риск: объём задания большой (11 пунктов «Обязательно» + веб-интерфейс
  + замеры). Митигация: этапы M0–M3, вертикальный срез на M1, приоритет
  «Обязательно» над «Желательно», честная фиксация долгов в `docs/known-issues.md`.
- **Совместная работа.** Риск: конфликты в git при параллельной работе.
  Митигация: работа в ветках, Pull Request, `git pull --rebase` перед push,
  разделение зон ответственности.

## 6. План этапов

- **M0. Дизайн (1–2 недели).** Design doc: границы сервиса, черновик API, схема
  данных, стек с обоснованием, риски, план этапов. Согласуется до начала кода.

  тесты, `docker-compose.yml`, `openapi.yaml` (черновик), `/health`, `/ready`.

  callback'и, идемпотентность, пагинация.
