# Design doc — apc-layers

Этап M0. Согласуется с заказчиком до начала кода.
Требования не пересказываем: они в `brief.md` и `common-requirements.md`. Здесь —
**как** мы их выполняем. Принятые решения с обоснованием — в `docs/decisions.md`
(ссылки вида ADR-NNNN), открытые вопросы — в `docs/questions.md`.

## 1. Границы сервиса

**Делает:** принимает сетки поставщиков, наборы точек и полигоны; хранит их с версиями;
строит из точек слои (KDE, биннинг, картограмма); считает статистику и классы; рисует
растровые тайлы в EPSG:3857 и EPSG:3395; отвечает на запросы к данным (значение в точке,
пакет точек, агрегат по полигону/bbox, рейтинг); даёт веб-интерфейс для загрузки,
настройки и проверки.

**Не делает:** не ходит в базу платформы и не знает её сущностей (щиты, заказы) —
«значения под щитами» платформа получает, присылая координаты щитов пакетом; не хранит
персональные данные (у точек — только то, что прислали; удаление ручкой и по сроку хранения, §9);
не геокодирует адреса в обязательном объёме (желательный адаптер — после M2);
не ходит во внешние платные сервисы.

**Главная идея архитектуры.** Любой источник (квадраты, шестиугольники, H3, районы,
результат KDE) приводится к одной абстракции — **сетка** (`grid`: набор ячеек
с номерами `0..N-1`) плюс **массив значений** версии слоя (`float32[N]`, `NaN` =
«неизвестно»). Всё остальное — тайлы, значения, агрегаты, рейтинг, статистика,
стили — пишется один раз поверх пары «сетка + массив» и одинаково работает для
слоёв поставщиков и слоёв из точек.

## 2. Компоненты и поток данных

```
            ┌─────────────┐  HTTP /v1, /ui
 платформа ─┤  api (×2)   │──────────────┐
 браузер   ─┤ FastAPI     │              │ чтение массивов / тайлов
            └──────┬──────┘              ▼
                   │ jobs (SQL)     ┌──────────────┐
            ┌──────▼──────┐         │ кэш на диске │  (общий volume)
            │ PostgreSQL  │◄────────┤ + S3 (MinIO) │
            │ + PostGIS   │         └──────▲───────┘
            └──────▲──────┘                │ артефакты
                   │ SKIP LOCKED    ┌──────┴───────┐   ┌──────────────────┐
                   └────────────────┤ worker       ├──►│ parser-подпроцесс│
                                    │ (тот же образ)│   │ rlimit, без сети │
                                    └──────────────┘   └──────────────────┘
            Redis: rate limit (горячий кэш PNG — только если покажет замер)
```

Поток импорта: файл (multipart / URL с защитой от SSRF / объект S3) → S3 + sha256 →
задание `inspect` (формат, колонки, тип геометрии, CRS, 20 строк предпросмотра) →
клиент подтверждает **манифест** → задание `import`: парсер в подпроцессе потоково
читает файл и пишет чанки Parquet → воркер сопоставляет ячейки с сеткой, пишет новые
ячейки в PostGIS, собирает массивы значений, считает статистику → версии в статусе
`draft` + отчёт об ошибках → `publish` строит пирамиду обзоров (п. 5.3) и делает
версию текущей.

Поток тайла: подпись → кэш на диске → при промахе рендер из «тайла индексов»
сетки + массива значений + стиля → PNG → кэш.

## 3. Схема данных

PostgreSQL хранит метаданные, геометрию ячеек и точки. **Значения сеток в строки
не раскладываем**: 10 млн ячеек × 10 метрик × 20 периодов — это 2 млрд строк, что
на 4 ГБ не живёт. Значения версии — один файл `float32[N]` (40 МБ на 10 млн ячеек)
в S3 с локальной копией на диске; api открывает его через `mmap` (ADR-0004).

| Сущность | Ключевые поля | Комментарий |
|---|---|---|
| `namespace` | id, title | Граница приватности. Есть служебный `shared` для данных поставщиков |
| `token` | id, hash (sha256), scopes, namespace, revoked_at | Токены в БД, отзыв без перезапуска |
| `file` | id, sha256, size, format, s3_key | Исходник, хранится как есть |
| `import` | id, file_id, manifest (jsonb), manifest_hash, report (jsonb) | `unique(file.sha256, manifest_hash, namespace)` → дедупликация |
| `provider`, `dataset` | id, namespace, provider, title | Набор = логическая группа слоёв одного поставщика |
| `grid` | id, kind, crs, params (jsonb), cell_count, fingerprint | `kind`: `rectilinear` · `h3` · `quadkey` · `polygons` |
| `grid_cell` | grid_id, idx int, key text, geom (4326), area_m2, attrs | `unique(grid_id,key)`, GiST по geom. Ячейки только добавляются |
| `layer` | id, dataset_id \| derivation_id, slug, title, unit, **value_kind**, default_style_id | `value_kind`: `intensive` (среднее, доля) · `extensive` (счётчик, сумма) |
| `layer_version` | id, layer_id, period, revision, grid_id, status, values_key, stats (jsonb), import_id | `status`: `draft · published · archived`; текущая = последняя опубликованная по периоду |
| `point_set` / `point_set_version` | id, namespace, schema / version_no, count, parquet_key | Пополнение = новая версия; снимок версии — Parquet для воркеров |
| `point` | set_id, added_in_version, geom, weight, category, ts, attrs jsonb | Таблица секционирована по set_id |
| `derivation` | id, source (point_set_id, version), method, params, auto_rebuild | Происхождение слоя из точек: по нему пересобираем при пополнении |
| `style` | id, revision, namespace, spec (jsonb) | Ревизия входит в URL тайла → смена стиля не требует сброса кэша |
| `job` | id, type, status, progress, attempts, token_id, idempotency_key, payload, result, error, heartbeat_at | Очередь на этой же таблице (ADR-0003). `status`: `queued · running · succeeded · failed` (общие требования §2) `· cancelled` (после `/cancel`; перечисление открытое) |
| `callback_delivery` | job_id, url, attempt, next_at, last_status | Outbox для callback'ов с повторами |

Ключевые правила:

- **Одна сетка на всех.** При импорте ячейки сопоставляются по ключу
  (`zone_id`, H3, quadkey) с существующей сеткой того же поставщика; если ключ
  совпал, а геометрия нет — предупреждение в отчёте и новая сетка. Новые ячейки
  дописываются в конец (`idx` растёт), старые массивы значений «короче» — хвост
  читается как `NaN`. Так три файла образца живут на одной сетке.
- **Полигоны (районы)** — это тоже сетка (`kind=polygons`): картограмма, рейтинг
  и агрегаты для них берутся из общего механизма.
- **«Неизвестно» ≠ 0.** Отсутствующая ячейка = `NaN` в массиве; в агрегатах и
  статистике не участвует, но учитывается в «доле покрытия».
- **Версии.** `(layer, period, revision)`; повторный импорт того же периода другим
  файлом — новая ревизия-черновик; публикация делает её текущей для периода, прежняя
  остаётся доступной по `version_id`. Тот же файл с тем же манифестом — возвращается
  существующий импорт (200, тот же `job_id`).
- **Агрегация** задаётся у слоя через `value_kind`, а не у набора: в одном файле
  бывают и доход (среднее), и рабочие места (сумма).

## 4. Импорт: форматы, геометрия, CRS

**Манифест** (JSON, его же собирает форма в UI):

```json
{
  "kind": "grid",
  "dataset": {"provider": "acme", "title": "Москва 500 м"},
  "period": "2023Q1",
  "geometry": {"type": "geojson"},
  "crs": "OGC:CRS84",
  "key": "zone_id",
  "metrics": [
    {"column": "val", "slug": "mean_income_home", "title": "Средний доход",
     "unit": "руб.", "value_kind": "intensive"}
  ],
  "options": {"max_error_rate": 0.01}
}
```

`geometry.type`: `geojson` (геометрия объекта) · `wkt` (колонка) ·
`center_size` (x, y, ширина, высота | радиус для шестиугольника) · `h3` · `quadkey` ·
`latlng` (только для точек). Несколько `metrics` = несколько слоёв из одного прохода.

**Чтение — потоковое, память не зависит от размера файла:** GeoJSON — `ijson`
(по объекту), NDJSON и CSV — построчно, XLSX — `openpyxl` read-only, GeoPackage /
Shapefile / GeoParquet — `pyogrio` (GDAL) батчами через Arrow. Парсер работает
в отдельном подпроцессе с `RLIMIT_AS`, `RLIMIT_CPU` и таймаутом, читает только
локальный файл и пишет чанки Parquet по 100 тыс. строк; падение парсера = падение
задания, а не воркера. ZIP/XLSX проверяются на бомбу до распаковки (суммарный
и относительный размер, число записей).

**Ошибки** не валят импорт: битая строка/геометрия попадает в отчёт
(первые 1000 с номером строки + счётчики по типам), задание падает только если
доля ошибок больше `max_error_rate`. Отчёт доступен через API и в UI.

**CRS:** из файла (GPKG, GeoJSON `crs`), иначе из манифеста, иначе EPSG:4326.
Эвристика «перепутаны lat/lng» — предупреждение. Геометрия хранится в 4326 (для
PostGIS-запросов), параметры сетки — в исходной CRS.

**Распознавание типа сетки** после чтения (это ключ к скорости, п. 5):

- `rectilinear` — все ячейки прямоугольники, выровненные по осям **своей** CRS
  (это и квадраты по параллелям, и ячейки в UTM/МСК, не выровненные на карте).
  Храним отсортированные массивы границ столбцов и строк. Так точнее, чем «один
  шаг»: в образце шаг по широте плавает в 6-м знаке (0,004395…0,004397).
- `h3`, `quadkey` — ключ сам задаёт геометрию; полигоны строим для PostGIS и UI.
- `polygons` — всё остальное (произвольные шестиугольники, районы).

## 5. Рендер тайлов

### 5.1. Тайл индексов сетки

Для каждого тайла считаем `uint32[256×256]` — номер ячейки под центром каждого
пикселя (или «пусто»). Он зависит **только от сетки и тайловой схемы** и не зависит
от версии, слоя и стиля, поэтому кэшируется один раз на все периоды и все метрики.

- `rectilinear`: границы тайла в метрах схемы (`morecantile`) → центры пикселей
  → `pyproj` в CRS сетки → `searchsorted` по границам → `idx`. Чистый numpy, ~2–5 мс.
- `h3` / `quadkey`: центры пикселей → индекс ячейки → словарь `key → idx`.
- `polygons`: ячейки из GiST по bbox тайла → проекция в схему тайла →
  `rasterio.features.rasterize`.

**EPSG:3395** отличается от 3857 только формулой широты (эллипсоид). Формулы сами
не пишем: обе схемы берём из `morecantile` (`WebMercatorQuad`, `WorldMercatorWGS84Quad`),
поэтому вторая схема — это другой параметр в одном месте кода, а не отдельный
конвейер. Тестируем по эталонным тайлам Яндекс.Карт v3 и по формулам (ADR-0006).

### 5.2. Крупные масштабы (ячейка ≥ ~2 px)

`PNG = palette[classify(values[index_tile])]`: выборка из `mmap`-массива,
`np.digitize` по границам классов, PNG в режиме палитры с `tRNS`. Ожидание —
10–30 мс на холодный тайл при кэшированном тайле индексов. `@2x` = 512×512 той же
логикой.

### 5.3. Мелкие масштабы (ячейка < ~2 px) — пирамида обзоров

При публикации версии строим пирамиду `float32`-тайлов от зума `z_s` (где ячейка
≈ 2 px) до 0, только там, где есть данные:

- `intensive` (доход, доля): среднее, взвешенное по площади ячеек внутри пикселя.
- `extensive` (счётчики): сначала плотность `val / area_km2`, затем среднее →
  на мелких зумах показываем **плотность на км²**, а легенда сама переключает единицу.
  Сумма на пиксель не годится: она зависит от зума.

Обзоры не зависят от стиля; их раскраска — та же функция, что в 5.2.

### 5.4. Кэш и заголовки

URL содержит `version_id` и `style@revision`, поэтому содержимое по URL неизменно:
`Cache-Control: public, max-age=31536000, immutable`, `ETag` = хэш ключа, на
`If-None-Match` — `304` без рендера. Кэш PNG — на диске
`tiles/{layer}/{version}/{style@rev}/{tms}/{z}/{x}/{y}.png` с вытеснением по объёму.
Сброс — удаление префикса; прогрев — задание по bbox и диапазону зумов.

## 6. Слои из точек

Все три метода дают **обычную версию слоя на обычной сетке** — дальше работают
стили, тайлы, значения, агрегаты и рейтинг без особых случаев.

- **KDE (метры).** Точки → локальная равновеликая проекция (LAEA с центром в bbox
  набора; для охвата больше ~1500 км — по регионам) → растр с шагом `h/4` → свёртка
  гауссовым ядром через FFT (`scipy.signal.fftconvolve`); ядро нормировано на 1, так
  что значение = **точек (или суммы весов) на км²**. Результат — сетка
  `rectilinear` в LAEA, `value_kind=intensive`. 1 млн точек — гистограмма за секунды;
  время задаёт размер растра, а не число точек.
- **Радиус в пикселях.** Чисто визуальный режим: считается на лету в рендере тайла
  из точек тайла и полей вокруг него. Легенда относительная (без единиц) — так и пишем
  в каталоге.
- **Биннинг.** Квадраты шага `S` м (в LAEA, чтобы площадь была честной) или H3
  уровня `r` → `count | sum(weight) | mean(field)` → сетка.
- **Картограмма.** Набор полигонов (это тоже сетка) × точки → пространственное
  соединение (`STRtree` в воркере) → число на полигон. Нормировки: `none`,
  `per_km2` (геодезическая площадь), `share` (доля от суммы), `per_layer`
  (делим на агрегат другого слоя по полигону × множитель, например «кафе на 100
  рабочих мест»). Рейтинг — общий механизм.
- **Категории:** `split` (слой на категорию одной командой) или `filter`.
- **Пополнение** набора даёт новую `point_set_version`; для `derivation` с
  `auto_rebuild=true` ставится задание пересборки → новая версия слоя.

## 7. Статистика, классы, стили, легенда

**Статистика** считается при импорте потоково: count, NaN-count, min/max, mean,
перцентили (1…99), гистограммы 64 бина (линейная и логарифмическая). Jenks
(`jenkspy`) — по выборке ≤ 20 тыс. значений.

**Стиль** (`style.spec`): палитра (имя или список цветов), число классов, метод
(`equal | quantile | log | jenks | manual`), `breaks_from` (`version` — границы
своего периода, `fixed` — общие, чтобы периоды можно было сравнивать по цвету),
непрозрачность, цвет «нет данных» (по умолчанию прозрачный), правила для зумов
(`min_zoom`, режим обзора). Новая ревизия стиля = новые URL тайлов, данные не трогаем.

**Легенда** = `legend(style, stats, zoom_mode)`; та же функция `breaks + palette`
используется рендером, поэтому картинка и легенда не расходятся по построению.

## 8. API (черновик; полный контракт — `openapi.yaml` с M1)

Общие правила — из `common-requirements.md` §2 (ошибки, jobs, курсоры, X-Request-Id).
**Идемпотентность:** заголовок `Idempotency-Key` на любой `POST` (хранится 24 ч,
повтор → тот же ответ) **плюс** дедупликация импорта по `sha256(файл) + hash(манифест)`.

| Метод и путь | Назначение | Доступ |
|---|---|---|
| `POST /v1/files` | Файл: multipart, `{url}` или `{s3:{bucket,key}}` → 202, задание `inspect` | write |

| `GET /v1/imports/{id}` | Отчёт об ошибках | read |
| `GET /v1/datasets`, `GET /v1/layers` | Каталог (фильтры, курсор), у слоя — версии, текущая, легенда, шаблон URL | read |
| `GET /v1/layers/{id}/versions/{v}` | Метаданные и статистика версии | read |

Большие файлы (сотни МБ – ГБ) не гоним через multipart api: клиент передаёт ссылку
или ключ S3, сервис качает сам потоково (лимит размера, таймауты, ≤ 3 редиректа,
только http(s), запрет приватных/локальных адресов после резолва DNS).

## 9. Доступ и безопасность

- **Токены** — в БД хэшем, scopes `admin | write | read`, привязка к namespace.
  Первый admin-токен — из env `BOOTSTRAP_ADMIN_TOKEN` при пустой таблице.
- **Подписанные ссылки.** Клиент сам подставляет `z/x/y`, поэтому подпись покрывает
  **префикс** пути: `sig = HMAC_SHA256(secret, "{prefix}|{exp}")`, где
  `prefix = /v1/tiles/{layer}/{version}/{style@rev}/{tms}/`. `exp` округляется вверх
  до шага `SIGN_EXP_ROUNDING_SECONDS` (по умолчанию 1 час) — URL стабилен в пределах
  шага и не ломает браузерный кэш. Тот же механизм
  со scope «values: список слоёв» — для значений под курсором в браузере. Поддерживаем
  два секрета одновременно для ротации без простоя.
- **Namespace:** точки, полигоны и производные слои видны только своему namespace;
  данные поставщиков лежат в `shared`, но отдаются только по токену или подписи.
- **CORS** — список origin из env. **Rate limit** — token bucket в Redis по токену
  или ключу подписи; дорогие ручки (`batch`, `aggregate`, холодные тайлы) — отдельная
  квота. Капы одновременных заданий на токен — при превышении 429 с `Retry-After`.
- **Callback'и** — outbox, подпись по §3 общих требований, 6 попыток
  (10 с, 30 с, 2 мин, 10 мин, 1 ч, 6 ч).
- **Персональные данные** (общие требования §6). В точках клиентов могут оказаться
  адреса, имена и т.п. в произвольных полях. Храним только присланное; в логах нет
  значений полей и координат. Удаление — `DELETE /v1/point-sets/{id}`. Срок хранения
  настраивается (`POINT_SETS_RETENTION_DAYS`, пусто = бессрочно): служебное задание
  раз в сутки удаляет наборы, не пополнявшиеся дольше срока. Производные слои при
  удалении набора остаются: в них только агрегаты по ячейкам, без исходных точек.
- **SIGTERM:** api дорабатывает текущие запросы; воркер дожидается конца текущего шага
  (шаги ≤ 30 с), иначе возвращает задание в очередь; зависшие по `heartbeat_at`
  подбираются заново.

## 10. Стек (подробно — ADR-0002…0007)

| Что | Выбор | Почему |
|---|---|---|
| Язык, HTTP | Python 3.12, FastAPI, uvicorn под gunicorn (2 процесса) | Сильная гео-экосистема; OpenAPI из кода; тяжёлое — в numpy и GDAL, а не в чистом Python |
| Гео и расчёты | numpy, scipy, pyproj, morecantile, shapely 2, pyogrio + GDAL, rasterio, h3, pyarrow, Pillow, jenkspy | Векторные операции на C; все лицензии MIT/BSD/Apache |
| БД | PostgreSQL 16 + PostGIS 3.4 | GiST, `ST_Intersects`, площади на геоиде, `ST_AsMVT` для желательного MVT |
| Очередь | Таблица `job` + `SELECT … FOR UPDATE SKIP LOCKED` | Задания уже нужны в БД (прогресс, повтор, идемпотентность); минус один брокер |
| Лимиты | Redis 8 (AGPL, отдельный неизменённый сервис) | Общий rate limit для двух процессов api; горячий кэш тайлов — только если замер покажет, что диска мало. Valkey 8 (BSD) — замена без изменения кода, если AGPL недопустим |
| Объекты | S3; локально MinIO | Исходники, массивы, обзоры, экспорт |
| Веб-интерфейс | Vue 3 (JavaScript) + Vite + MapLibre GL JS, собирается в статику на этапе сборки образа и раздаётся тем же api по `/ui` | Знакомый команде фреймворк; карта и формы манифеста интерактивные; UI ходит в тот же `/v1`, что и платформа (ADR-0010) |
| Миграции, линт, тесты | Alembic, ruff, mypy, pytest, uv (lock-файл) | Стандарт для Python |
| Замеры | k6 (тайлы, API) + pytest-benchmark (ядро) | Скрипты в `bench/` |

**Бюджет памяти на профиле 2 vCPU / 4 ГБ:** PostgreSQL 1 ГБ (`shared_buffers`
256 МБ) · Redis 64 МБ · MinIO 256 МБ · api 2×350 МБ · worker 300 МБ + парсер /
расчёт ≤ 1,2 ГБ (`RLIMIT_AS`) · запас ~0,4 ГБ. Одновременно выполняется одно тяжёлое
задание (настраивается).

## 11. Риски

| Риск | Что делаем |
|---|---|
| 200 rps / холодный тайл ≤ 300 мс на Python | Тайл индексов + массив значений → рендер = numpy; кэш PNG; замер на M1, а не на M3. Запасной план — оптимизация numpy и прогрев кэша, затем при необходимости рендер отдельным сервисом на Go (ADR-0002) |
| Сетка, которую не распознали как регулярную (10 млн полигонов) | Путь `polygons` медленнее, но корректен; тайлы индексов кэшируются и прогреваются заданием; замер на синтетике 10 млн |
| Файл 3 ГБ / враждебный файл | Потоковый разбор в подпроцессе с rlimit, проверки на бомбы, отчёт вместо падения |
| Несовпадение 3395 с Яндекс.Картами | Эталонные тайлы и тесты формул; сверка наложением в UI |
| Данные «не как в образце» | Набор синтетических сеток в тестах: H3, шестиугольники, 100 м и 5 км, UTM, районы, CSV с WKT, XLSX центр+размер, 10 метрик в файле |
| KDE на всю страну | LAEA по регионам, размер растра ограничен конфигом, иначе ошибка 422 с подсказкой увеличить полосу |
| Утечка лицензионных данных | Только токен или подпись; `shared` доступен лишь на чтение; в логах нет значений и координат точек |
| Объём работ | Вертикальный срез на M1, «желательно» — только после зелёного «обязательно» |

## 12. Тесты и замеры

Образец — только пример одного поставщика (brief), поэтому тесты строятся **не на
нём**, а на синтетических данных, где правильный ответ известен заранее по построению.

- **Генератор синтетики** (`tests/synth/`): сетки разных типов и параметров —
  квадраты 100 м … 5 км по параллелям, ячейки в UTM/МСК (на карте не выровнены),
  шестиугольники, H3 разных уровней, quadkey, районы-полигоны, «дырявые» сетки
  (пропуски = `NaN`), 10 метрик в файле; те же данные во всех форматах импорта
  (GeoJSON, NDJSON, CSV с WKT / центром+размером / H3, XLSX, GeoPackage). Значение
  ячейки кодирует её номер или координаты, поэтому ответ проверяется формулой.
- **Юнит:** проекции и тайловые схемы (эталонные точки 3857/3395), распознавание
  сеток, классификация, KDE (интеграл ядра = числу точек), нормировки, подписи,
  цикл воркера очереди (ADR-0003).
- **Проверка тайлов по построению:** для случайных пикселей тайла считаем
  «правильную» ячейку независимым путём (shapely: какая ячейка содержит центр
  пикселя) и сверяем с цветом в PNG. Работает для любой сетки и обеих схем, не
  требует хранить картинки-эталоны.
- **Интеграционные:** docker compose в CI, сквозной сценарий на синтетике всех
  типов; образец — один из прогонов, а не основа.
- **Эталоны PNG:** небольшой набор для регрессии (раскраска, прозрачность,
  `@2x`), генерируется из синтетики; образец — только для визуальной сверки
  наложением на Яндекс.Карты и OSM.
- **Контрактные тесты** против `openapi.yaml` (schemathesis) — с M2, когда API
  устоится.
- **Типы:** mypy в обычном режиме; строже — для ядра (проекции, подписи, очередь).
- **Замеры** (`bench/`, k6 из образа `grafana/k6` + скрипты загрузки) на профиле
  2 vCPU / 4 ГБ (`docker compose` с `cpus: 2`, `mem_limit` для сервиса, генератор
  нагрузки ограничен отдельно): тайл из кэша и холодный, rps, импорт образца и
  синтетики на 1 млн / 10 млн ячеек, 5 тыс. / 100 тыс. / 1 млн точек → слой. Отчёт — `docs/benchmarks.md`.
- **CI:** ruff, mypy, pytest, gitleaks, проверка лицензий (`pip-licenses`; для UI — `license-checker`), eslint и сборка UI (`vite build`).

## 13. План этапов

- **M0 (сейчас).** Этот документ, ADR, вопросы заказчику.
- **M1. Вертикальный срез.** Импорт GeoJSON-сетки (образец **и** синтетика:
  другой шаг, ячейки в UTM) → сетка `rectilinear` →
  версия → публикация → тайлы **3857 и 3395** с подписью и кэшем → значение в точке.
  Минимальная страница `/ui` с картой MapLibre. `docker compose up`, `/health`,
  `/ready`, Docker-образ по общим требованиям §4 (multi-stage, запуск не от root,
  `HEALTHCHECK`, зафиксированные версии), черновик `openapi.yaml`, CI (ruff, pytest, gitleaks). **Первый замер
  тайлов** — проверка главного риска.
- **M2. Полный объём.** Остальные форматы и типы сеток, точки и три метода, полигоны,
  стили и классы, легенда, пакет значений, агрегаты, рейтинг, обзоры на мелких зумах,
  токены и namespace, callback'и, лимиты, весь веб-интерфейс, полный OpenAPI с контрактными тестами (schemathesis).
- **M3. Закалка.** Замеры и оптимизация, отчёт, README / runbook, known-issues, демо.
  Из «желательно» по приоритету: MVT → PMTiles → картинка области → Shapefile /
  GeoParquet → несколько слоёв по категориям одной командой.

**Можно подумать (в дизайне, не в коде).** Производные слои (разница периодов,
взвешенная сумма) — новый `derivation.method` поверх массивов одной сетки: разница
периодов — это поэлементная операция над `float32[N]`. Слои по времени — точки
с `ts` → `period` на бин → обычные версии; анимация в UI — перебор версий.
